# このプロジェクトについて

このプロジェクトは、`Agentic Coding` を行う Coding Agent が
プロジェクト内のファイルを探したり、読むべきファイルを絞り込んだりする際に、
毎回 `Glob` や `Grep` に強く依存しなくてもよい状態を作ることを目的とする。

発想の中心は単純で、
**ファイルの位置と内容からタグを生成し、そのタグを探索の一次索引にする**
というもの。

`Agent Skill`、`MCP`、`SubAgent` はいずれも有効な手段ではあるが、
「どのファイルを見るべきか」を毎回ゼロから解く問題を直接は解決しない。
このプロジェクトでは、まずそこを構造化する。

## 目指す状態

理想は、Coding Agent がユーザーの依頼を受けたときに、
次の流れで対象ファイルへ到達できること。

1. 依頼文から「欲しいファイルの性質」を抽出する
2. その性質に対応するタグで候補ファイルを数個まで絞る
3. 絞ったファイルだけを読んで判断する
4. 必要な場合だけ `Glob` や `Grep` にフォールバックする

つまり、`Glob` や `Grep` を完全に禁止したいのではなく、
**常用しなくても済む状態にしたい**。

## なぜタグ方式なのか

ファイル探索は本来、以下の 2 つの問題に分かれる。

- どのファイルを開くべきか
- 開いたファイルが本当に目的に合うか

`Glob` は主に前者、`Grep` は主に後者に効くが、
どちらも毎回フルスキャン寄りの思考になる。

一方で、実際のソフトウェア開発では多くのファイルに
ある程度安定した「役割」と「置かれ方」がある。
たとえば、

- `src/features/auth/...` にある
- `route`, `handler`, `service`, `repository` のような語を持つ
- `test`, `spec`, `fixture`, `migration` のような責務を持つ
- `React`, `SQL`, `OpenAPI`, `Prisma`, `Cargo` などの技術語を持つ

といった特徴は、探索のヒントとしてかなり強い。

この強い特徴を先にタグとして保持しておけば、
Agent は全文検索ではなく「意味つきの候補絞り込み」から始められる。

## 基本方針

タグは大きく分けて、以下の 3 層で扱う。

### 1. 位置タグ

ファイルパスとディレクトリ構造から機械的に決まるタグ。

例:

- `depth:1`
- `dir:src`
- `dir:features`
- `path:src/features/auth`
- `ext:rs`
- `name:main`

これは最も安定していて、誤判定しづらい。
最低限、この層だけでも探索性能はかなり改善する。

### 2. 役割タグ

そのファイルが何を担当しているかを表すタグ。

例:

- `role:entrypoint`
- `role:ui`
- `role:api-route`
- `role:service`
- `role:repository`
- `role:model`
- `role:test`
- `role:config`
- `role:docs`
- `role:migration`

これはファイル名、ディレクトリ名、拡張子、代表的な識別子から推定する。
Agent が最初に欲しいのは、実際にはこの層であることが多い。

### 3. 内容タグ

ファイル内に現れる語や構文から抽出するタグ。

例:

- `kw:login`
- `kw:payment`
- `kw:cache`
- `tech:react`
- `tech:tokio`
- `tech:sql`
- `tech:prisma`
- `side-effect:network`
- `side-effect:file-io`

これは探索精度を上げる一方で、ノイズも増えやすい。
そのため、単語の出現回数だけではなく、
「どの種類の語か」を区別して扱う必要がある。

## タグ設計で重要な観点

### 決定的なタグと推定タグを分ける

すべてのタグを同じ重みで扱うと、探索品質が崩れる。

- 決定的タグ: パス、拡張子、明確なファイル名規則から決まるもの
- 推定タグ: 内容や命名から推定するもの

たとえば `ext:rs` や `dir:src` はほぼ確定だが、
`role:service` は規約次第では外れる。

そのためタグには、少なくとも以下の属性を持たせたい。

- `tag`
- `source` (`path`, `filename`, `content`, `ast`)
- `confidence`

## タグの付与ルール

### 位置に基づくタグ

これは完全に機械生成でよい。

- ルートからの深さ
- 親ディレクトリ名
- 拡張子
- ファイル名
- 特定パスパターンへの一致

例:

- `src/main.rs` -> `dir:src`, `name:main`, `ext:rs`, `role:entrypoint`
- `docs/api/auth.md` -> `dir:docs`, `dir:api`, `kw:auth`, `role:docs`

### 内容に基づくタグ

内容タグは、少なくとも次の 3 段階に分けると扱いやすい。

1. 文字列レベル
2. 構文レベル
3. 規約レベル

#### 1. 文字列レベル

- 頻出単語
- 特徴語の有無
- import / use / require の対象

最も簡単だが、ノイズが多い。
コメントやサンプルコードに引っ張られる。

#### 2. 構文レベル

- 関数名
- 型名
- クラス名
- エクスポート名
- attribute / annotation

これは文字列レベルよりかなり信頼できる。
可能なら AST ベースで抽出したい。

#### 3. 規約レベル

- `*.test.ts` なら `role:test`
- `page.tsx` なら `role:page`
- `route.ts` なら `role:api-route`
- `mod.rs` ならモジュール境界候補

これはプロジェクトやフレームワークの慣習を強く使う。
精度が高い反面、言語やフレームワークごとの定義が必要になる。

## Agent の探索フロー

Agent がタグを使って探索する場合の基本フローは以下。

1. ユーザー要求を探索条件へ分解する
2. 必須条件と加点条件を分ける
3. 必須条件で候補を絞る
4. 加点条件で順位付けする
5. 上位数件だけを開く
6. 不足時のみ `Grep` / `Glob` にフォールバックする

たとえば、
「認証まわりの API ハンドラを直したい」という要求なら、
探索条件は次のように分解できる。

- 必須候補: `kw:auth` または `kw:login`
- 必須候補: `role:api-route` または `role:handler`
- 加点候補: `dir:src`, `dir:features`, `tech:http`

この分解ができれば、全文検索をしなくても
かなり少ないファイル数まで絞れる。

## 読むべきファイルと、読まなくてよいファイルを分ける

Agent にとって重要なのは「候補を見つけること」だけではなく、
**読まなくてよいファイルを早く除外できること**でもある。

そのため、除外タグも重要になる。

例:

- `kind:generated`
- `kind:vendor`
- `kind:lockfile`
- `kind:artifact`
- `kind:fixture`
- `kind:deprecated`

これらが付いていれば、Agent は初手で除外しやすい。
探索コストの削減には、加点タグより除外タグの方が効く場面も多い。

## 前提条件

元の発想では、

- ディレクトリ構成がコロケーションである
- 各ファイルが単一責任に近い

という前提が置かれている。

この方向性は正しいが、README としては
「前提が崩れたら使えない」では弱い。
むしろ、次のように言い換えた方が実用的である。

- コロケーションであるほど位置タグの精度は上がる
- 単一責任であるほど内容タグの精度は上がる
- ただし完全に満たしていなくても、位置タグだけで一定の価値はある

つまりこの仕組みは、
理想的な設計を要求するというより、
**設計品質が高いほど検索性能が上がる索引方式**
として捉える方がよい。

## 失敗しやすいケース

以下のようなケースでは、タグ方式だけでは精度が落ちやすい。

- 1 ファイルに責務が多すぎる
- 命名が抽象的すぎる
- generated code が大量に混ざる
- プロジェクト固有の略語が多い
- パス構造と責務が一致していない

そのため、
タグ方式は `Grep` の完全な代替ではなく、
**高精度な候補削減レイヤー**
として扱うのが現実的である。

## 評価指標

このプロジェクトが有効かどうかは、
「タグが作れたか」ではなく
「Agent が少ない試行で目的ファイルに到達できたか」で判断すべき。

見るべき指標の例:

- Top-K に目的ファイルが含まれる率
- 1 タスクあたりに開いたファイル数
- `Grep` / `Glob` へのフォールバック率
- タグ生成時間
- タグの更新コスト

特に重要なのは、
**探索精度** と **運用コスト** の両立である。

## 今後さらに詰めるべき論点

README を次の段階に進めるなら、少なくとも以下は定義したい。

### 1. タグの正式スキーマ

少なくとも以下を決める必要がある。

- タグ名の命名規則
- 階層表現の有無
- `source`
- `confidence`
- 単一値か複数値か

### 2. 検索クエリの表現

Agent がどうやってタグを問い合わせるかを定義したい。

例:

- `role:api-route AND kw:auth`
- `dir:docs AND tech:openapi`
- `role:test AND related:payment`

ここが曖昧だと、タグがあっても探索戦略へ落とし込めない。

### 3. タグ生成器の責務

タグ生成器がどこまでやるのかも決めるべき。

- 単純なパス解析だけか
- 内容解析までやるか
- AST を使うか
- 言語別プラグイン方式にするか

### 4. フォールバック条件

タグだけで答えが出ないときに、
いつ `Grep` や `Glob` へ落ちるのかを定義したい。

例:

- 候補件数が多すぎる
- 上位候補の confidence が低い
- タグに一致する候補が存在しない

## 現時点での設計仮説

最初に作るべきものは、万能な意味解析器ではなく、
以下の順で小さく始める方がよい。

1. パス由来のタグを確実に付ける
2. ファイル名規約から役割タグを付ける
3. 少数の高精度キーワードだけ内容タグ化する
4. Agent から使う検索 API を定義する
5. 足りない部分だけ `Grep` にフォールバックする

つまり、最初から全文理解を目指すのではなく、
**高信頼タグを中心に探索面を最適化する**
のがこのプロジェクトの現実的な出発点になる。
